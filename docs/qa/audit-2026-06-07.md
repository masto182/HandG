## 1. Executive Summary

**Overall quality assessment:** The membership gating and server-side permission model — the highest-risk part of a members-only commerce app — is **genuinely solid**. Guest/non-member users are correctly denied prices, ABV, Untappd scores, stock, add-to-cart, and wishlist both in the rendered UI and at the API layer (verified by direct payload diff). Registration, approval, and login all work; age and referral validation are enforced. This is materially better than the prior build notes implied.

However, the app is **not launch-ready** as-is. There is a **cluster of client-side runtime errors on core pages** (React hydration mismatches on `/`, `/store`, PDP, and `/account`; a `TypeError: frame.join is not a function` on the homepage caught by the error boundary; a `SyntaxError` on the homepage). These degrade reliability and perceived quality on the most-trafficked routes and must be resolved before launch. Several **UX gaps** (silent unexplained redirects from `/cart` and `/checkout`, inconsistent guest handling of `/account/*` sub-routes) and a **broad set of admin destructive actions with no confirmation** add operator-error and trust risk. A **data-integrity latent bug** in the buy-at-price approval path can lock a promotion price at $0.

**Issue counts by severity (issues confirmed so far):**

### F1 — Index Engine product `count` desync — HIGH

- Category: Functional/Data · Roles: all · Component: `/store/products`, Medusa Index Engine
- **Repro:** `GET /store/products?limit=1` → `count: 2`. DB has **15** published products; the endpoint still returns the requested products. Persists after `just seed-e2e`.
- **Expected:** `count` equals total matching products (15, or 14 after future-release filter).
- **Actual:** `count: 2`. The storefront listing counter is masked to a correct "14 RELEASES FOUND" by a defensive `Math.max(visible.length, …)` patch, but any consumer using `count` directly (pagination total pages, API clients, admin lists) will be wrong.
- **Why it matters:** Silent data-correctness bug; pagination breaks past page 1 once catalog > page size; admin product lists historically showed blank rows from the same root cause.
- **Suspected root cause:** Stale `index_data`/`index_relation`/`index_metadata`; products seeded after index build. Memory documents the fix: truncate the 4 index tables + restart backend, or full `indexModule.sync`.
- **Fix:** Add a post-seed reindex step to the seed/CI chain; investigate why incremental index updates don't keep `count` in sync. [Proven]

### F2 — React hydration mismatch on multiple core pages — HIGH

- Category: Functional/Reliability · Roles: all · Pages: `/`, `/store`, `/products/[handle]`, `/account` (the documented one was only `/breweries`)
- **Evidence (console, guest pass):** `Uncaught Error: Hydration failed because the server rendered HTML didn't match the client...` plus `Uncaught TypeError: Cannot read properties of null (reading 'parentNode')` on `/` and PDP.
- **Why it matters:** React discards and regenerates the subtree on the client → content flashes, interactivity can break, and it masks other errors. Occurs on the highest-traffic routes.
- **Suspected root cause:** Time-dependent server vs client rendering (e.g. New Arrivals "NEW < 7 days" badge, early-access countdowns, or `Date.now()`/locale formatting) rather than the theme toggle (the toggle's initial state is deterministically `"dark"` on both server and client — verified; not the cause).
- **Fix:** Move time/locale-dependent rendering to client-only (`useEffect`) or gate with `suppressHydrationWarning` where genuinely dynamic; audit New-Arrivals badge + countdown components. `/breweries` already has a known mismatch (its hydration test is permanently skipped). [Proven]

### F3 — Homepage runtime `TypeError: frame.join is not a function` — HIGH

- Category: Functional · Role: all · Page: `/` (`<Home>` component)
- **Evidence:** `TypeError: frame.join is not a function` in `<Home>`, caught by `<ErrorBoundaryHandler>`, plus a paired `Global error`.
- **Why it matters:** A real runtime exception on the landing page, currently swallowed by the error boundary — fragile and easily becomes a visible crash.
- **Suspected root cause:** Not literal in source (`grep` found no `frame.join`); likely a cascade of the dev error-overlay/hydration failure (F2) or a third-party (e.g. framer-motion) frame handler receiving a non-array. Resolve F2 first, then re-check.
- **Fix:** Reproduce with the error boundary disabled in dev; trace the failing `frame` value. [Proven]

### F8 — Buy-at-price approval can lock a promotion at $0 — MEDIUM (latent data integrity)

### 9.3 Membership lifecycle API — NEW HIGH FINDING

**F-NEW-1 — Suspend/reject does not block login [HIGH-SECURITY]**

Script ran against fresh customer `qa-lifecycle3@hg-test.dev`. After `POST /admin/members/{id}/suspend` (200) and `POST /admin/members/{id}/reject` (200), `POST /auth/customer/emailpass` still returned **200** (expected: 401).

**Root cause confirmed:** `set-auth-identity-disabled` step (`apps/backend/src/workflows/steps/set-auth-identity-disabled.ts`) calls `authModule.updateAuthIdentities({ id, provider_metadata: {disabled: true} })`. But `auth_identity` has no `provider_metadata` column (confirmed via `\d auth_identity`). The column belongs to `provider_identity`. The `disabled` flag is written to a non-existent field and silently ignored. Medusa's emailpass provider reads `provider_identity.provider_metadata.disabled` — which is never set.

**Impact:** Suspended or rejected customers can still authenticate and receive a valid JWT indefinitely. Any downstream access gate (e.g. cart, wishlist, checkout) that trusts the JWT without re-checking group membership is bypassable.

**Fix:** In `set-auth-identity-disabled`, use `authModule.listProviderIdentities` (or raw DB) to find the `provider_identity` rows linked to this customer and update `provider_identity.provider_metadata` instead. Verify emailpass actually gates on this flag after fix.
